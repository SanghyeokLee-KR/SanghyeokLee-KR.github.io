01개요

개발자들이 UI와 코드를 나누는 커뮤니티를, 네 명이 한 달 반 동안 만들었습니다

DevHub는 게시판과 코드 스니펫, 팀 모집, 포인트 충전과 출석, 실시간 채팅, AI 챗봇이 있는 개발자 커뮤니티입니다. Spring Boot와 Thymeleaf로 서버에서 화면을 그립니다. 2024년 인천일보아카데미에서 4인 팀으로 만들었고, 저는 PM으로 ERD를 설계하면서 인증과 보안, 결제창 연동, 실시간 채팅, 챗봇을 구현했습니다.

팀 프로젝트가 끝난 뒤 코드를 다시 열어 보니 고칠 곳이 보였습니다. 꺼져 있던 Spring Security를 다시 켜고, 포인트 계산의 버그를 고치고, 외부 키가 없어도 앱이 뜨게 바꾼 뒤, 그 규칙들을 테스트로 묶었습니다. 지금은 Oracle과 외부 키 없이 명령 한 줄로 실행됩니다.

02맡은 기능

로그인부터 결제창, 채팅, 챗봇까지 화면과 서버를 함께 만들었습니다

  1. 회원가입과 세션 로그인이메일 인증을 거치는 3단계 가입 화면부터 서버까지 만들었습니다. 없는 아이디와 틀린 비밀번호에는 같은 문구를 보여 줘, 계정이 있는지 드러나지 않게 했습니다.
  2. 실시간 채팅엔드포인트는 /ws, 브로커는 /topic입니다. /app/chat.sendMessage로 받은 메시지를 /topic/public으로 다시 보냅니다.
  3. 결제창 연동프런트에서 iamport로 카카오페이 결제창을 띄우고, 결제가 끝나면 /charge로 포인트를 적립하면서 구매 내역 저장과 안내 메일 발송을 함께 처리합니다.
  4. AI 챗봇사용자 메시지를 Dialogflow로 보내 의도를 분석하고 답하는 안내 챗봇입니다. 인증 키는 저장소에 올리지 않습니다.

03프로젝트가 끝난 뒤 다시 고친 것

로그인한 사용자까지 막던 Security를, 세션과 이어 다시 켰습니다

세션에 아이디를 담는 커스텀 로그인을 쓰다 보니, Spring Security는 로그인한 사용자가 누구인지 몰랐습니다. 켜면 로그인한 사용자까지 막혔고, 그래서 팀 프로젝트 때는 꺼 두었습니다. 끈 채로는 프레임워크 차원의 인가가 아예 없었습니다. 끝난 뒤 다시 열어, 요청마다 세션의 아이디를 SecurityContext에 올려 주는 필터를 넣고 민감한 경로만 로그인을 요구하게 했습니다. 아래 그림에서 요청 하나가 어디까지 가는지 볼 수 있습니다.

저장소의 계층 구조도를 옮겨 그렸습니다. 장면의 결과는 저장소 테스트로 확인하는 규칙입니다.

  1. Security

    Security를 켜면 모든 요청이 막혔습니다

    세션 로그인 정보를 요청마다 SecurityContext에 올려 주는 OncePerRequestFilter를 넣고, 회원 수정 · 글쓰기 · 결제 · 출석 같은 경로만 authenticated()로 묶었습니다. 로그인하지 않았으면 /login으로 보냅니다.

  2. 포인트

    음수를 빼면 포인트가 오히려 늘었습니다

    '현재 − 차감액'에 음수가 들어가면 더해지는 셈이었고, '현재 ≥ 차감액' 조건도 늘 통과했습니다. 0 이하 차감을 거부하고 잔액이 충분할 때만 빼도록 고쳤고, 트랜잭션은 서비스 계층에 두었습니다.

  3. 챗봇 키

    챗봇 키 하나 때문에 앱이 뜨지 않았습니다

    키 파일은 .gitignore 대상이라 새로 클론하면 없는데, 기동할 때 챗봇 클라이언트를 무조건 만들고 있었습니다. 키 파일이 있을 때만 빈을 만들고, 서비스는 ObjectProvider.getIfAvailable()로 받아 키가 없으면 안내 문구를 돌려줍니다.

// SessionAuthenticationFilter · 요청마다 세션의 아이디를 인증 주체로
HttpSession session = request.getSession(false);
if (session != null
    && session.getAttribute("loginId") != null) {
  var auth = new UsernamePasswordAuthenticationToken(
      loginId, null, List.of(ROLE_USER));
  SecurityContextHolder.getContext()
      .setAuthentication(auth);
}
chain.doFilter(request, response);

// OrderService.deductPoints · 0 이하 차감 거부
if (MPoint <= 0) return 0;
if (currentPoints >= MPoint) { ... }

줄여서 옮겼습니다. 원문은 저장소의 config/SessionAuthenticationFilter.java, service/OrderService.java에 있습니다.

그 밖에 끝난 뒤 정리한 것6건 펼쳐 보기
  1. 키와 비밀번호를 설정에서 분리했습니다노출돼 있던 값을 별도 설정 파일로 옮기고 .gitignore를 정비했습니다.
  2. 트랜잭션 경계를 서비스 계층에 두었습니다외부 API 호출도 서비스에서 합니다.
  3. 업로드 경로를 바깥으로 뺐습니다방금 올린 프로필 사진이 바로 보이지 않던 문제였습니다. 저장과 제공 위치를 외부 uploads 폴더로 맞추니 바로 뜨고, JAR로 묶어도 동작합니다.
  4. 접속 위치 조회 토큰을 서버로 옮겼습니다조회 토큰이 브라우저에 보이지 않게 서버가 대신 조회하고, 기록하는 IP도 요청에서 직접 뽑습니다.
  5. 데모 데이터와 한 줄 실행H2 프로파일에서 회원 · 게시글 · 구매 · 출석 데모 데이터가 자동으로 들어가, 외부 키 없이 바로 둘러볼 수 있습니다.
  6. 테스트 17건과 빌드 CIGitHub Actions가 JDK 21에서 빌드와 테스트를 돌립니다.

04구조

요청은 Security, 컨트롤러, 서비스, 리포지터리 순서로 내려갑니다

트랜잭션 경계는 서비스에 두고, 챗봇 · 결제 · 위치 조회 같은 외부 API도 서비스에서 부릅니다. 채팅만 WebSocket(STOMP)으로 따로 들어옵니다. DB는 운영에서 Oracle, 데모에서 H2를 씁니다.

05테스트로 묶은 규칙

고친 것이 다시 깨지지 않도록, 규칙마다 테스트를 붙였습니다

무엇을확인하는 규칙건수
세션 로그인비밀번호가 맞으면 세션과 접속 이력이 남고, 틀리면 세션을 만들지 않습니다. 없는 아이디도 같은 문구로 답합니다.3
포인트 차감음수 차감은 거부하고, 잔액보다 큰 금액은 빼지 않으며, 잔액이 충분하면 그만큼만 뺍니다.3
출석 적립같은 날 두 번 출석해도 한 번만 쌓이고, 적립 포인트(일요일 100, 평일 10)는 서버가 정합니다.2
AI 챗봇 경로인증 키가 없어도 500 대신 안내 문구를 돌려줍니다.1
앱 기동외부 키 없이 애플리케이션 컨텍스트가 올라옵니다.1
게시판 검색제목 · 작성자 검색은 맞는 글만, 없는 키워드는 빈 목록을 돌려줍니다.3
접속 IP 조회토큰이 없으면 외부 조회 없이 IP만 남기는 등, 접속 이력에 남길 값을 정합니다.4

팀 프로젝트는 끝났지만, 다시 열어 보니 고칠 곳이 보였습니다. 하나씩 고치고, 다시 깨지지 않게 테스트로 묶었습니다.

팀 프로젝트 때는 Security를 꺼 두었습니다. 다시 켜 보니 기존 로그인 흐름을 그대로 두고도 인가를 붙일 수 있었습니다. 기능을 만드는 일과, 그 기능이 계속 맞게 동작하도록 지키는 일은 따로 챙겨야 한다는 걸 배웠습니다.
