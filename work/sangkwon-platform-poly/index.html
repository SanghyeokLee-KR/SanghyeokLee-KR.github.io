01개요

서울시 공공데이터로 상권을 비교하는 서비스를 만들고 배포했습니다

서울시가 공개한 상권 데이터를 카카오맵 위에 올려, 상권 1,650곳의 매출과 유동인구, 점포 수를 지도에서 바로 비교하는 서비스입니다. 네 명이 7월 3일부터 14일까지 만들었습니다.

배포는 EC2 두 대로 했습니다. 서버가 두 대가 되면 로그인 세션, 스케줄러, 요청 제한처럼 서버 안에 두던 상태가 서버마다 달라집니다. 이 상태를 DB로 옮긴 뒤, 한 대씩 교체하는 롤링 배포를 구성했습니다.

1,650곳

지도에서 비교하는 서울 상권

매출 · 유동인구 · 점포 수 · 상권 변화.

220만 행

전체 재적재하는 서울시 데이터 7종

점포 통계 하나만 160만 행입니다.

02운영 구성 · AWS 서울 리전

가용 영역 a·c의 EC2 두 대와 ALB 구성

요청은 HTTPS로 ALB에 들어오고, 두 EC2가 나눠 받습니다. DB는 Oracle Autonomous DB이고, Wallet으로 접속합니다.

서버 앞에 nginx는 따로 두지 않고 ALB에 맡겼습니다.

  1. 인증서는 ACM, 헬스체크는 30초마다ALB가 ACM 인증서로 TLS를 종료하고, /actuator/health를 30초마다 확인해 응답하지 않는 서버를 대상에서 뺍니다.
  2. systemd로 jar 실행앱은 systemd 서비스로 돌고, 죽거나 메모리가 바닥나면 Restart=always로 다시 올라옵니다.
  3. 8080 포트는 ALB에서만 허용8080 포트의 인바운드는 ALB 보안 그룹에서 오는 요청만 허용했습니다.

03롤링 배포

EC2를 한 대씩 교체하는 배포 순서

새 버전을 올릴 때 두 서버를 한꺼번에 내리지 않고, 한 대를 바꾸는 동안 다른 한 대가 요청을 모두 받도록 순서를 정했습니다. 내려가는 서버는 처리 중인 요청을 마저 끝내고, 그사이 ALB 헬스체크가 그 서버를 대상에서 뺍니다.

  1. bootJar

    한 번만 빌드

    jar는 로컬에서 한 번만 만들어 두 서버에 똑같이 올립니다. 서버마다 버전이 달라질 일이 없습니다.

  2. EC2-A

    A를 먼저 교체

    새 jar를 올리고 서비스를 다시 시작합니다. 그동안 요청은 B가 받습니다.

  3. health

    A가 돌아오면

    A가 헬스체크를 통과해 대상에 다시 들어온 뒤에만 다음으로 넘어갑니다.

  4. EC2-B

    B도 같은 순서로

    이번에는 A가 요청을 받습니다. 문제가 생기면 이전 jar로 같은 순서를 되밟아 돌아갑니다.

04상태 DB 이전

두 서버가 함께 봐야 하는 상태 네 가지

두 서버가 함께 봐야 하는 상태는 모두 DB로 옮겼습니다. 그래서 ALB 세션 고정 없이 서버를 대상 그룹에 추가할 수 있습니다.

상태서버에 두었다면옮긴 곳
로그인 세션다른 서버로 가면 다시 로그인Spring Session JDBC
스케줄러서버 수만큼 겹쳐 실행ShedLock
요청 제한서버 수만큼 한도가 느슨해짐RATE_LIMIT_BUCKET
데이터 재적재같은 적재가 동시에 실행함수 기반 유니크 인덱스

05공공데이터 재적재

220만 행을 다시 넣는 동안에도, 잘린 데이터가 보이지 않게 했습니다

상권 데이터는 분기마다 새로 나옵니다. 매출과 유동인구, 점포 수 같은 데이터를 지우고 다시 넣는데, 중간에 API 페이지가 비거나 제약을 어긴 행이 섞이면 반쯤 잘린 데이터가 커밋될 수 있었습니다. 서버가 두 대라 같은 데이터셋을 동시에 적재할 위험도 있었습니다.

  1. BEGIN

    지우고 넣기를 한 번에

    DELETE와 INSERT를 한 트랜잭션에 묶어, 커밋 전까지 화면은 이전 데이터를 그대로 봅니다.

  2. INSERT × 5,000

    5,000행씩 넣습니다

    묶음 하나가 실패하면 그 묶음만 한 줄씩 다시 넣습니다.

  3. total

    받은 건수를 맞춰 봅니다

    API가 알려 준 전체 건수보다 적게 받았거나, 건너뛴 행이 하나라도 있으면 전부 롤백합니다.

  4. COMMIT

    검증을 통과하면 커밋

    모든 확인을 통과해야 새 데이터가 한꺼번에 보입니다.

  1. 같은 적재가 두 번 돌지 않게함수 기반 유니크 인덱스로, 데이터셋마다 실행 중인 기록이 하나만 있을 수 있게 했습니다. 다른 서버의 적재와 겹치면 나중 것이 건너뜁니다.
  2. 멈춘 작업은 하트비트로 판단실행 중에는 5분마다 하트비트를 남기고, 서버가 켜질 때 15분 넘게 소식이 없는 작업만 실패로 정리합니다.
  3. 시작 시각으로 판단하지 않은 이유시작 시각만 보면 롤링 배포로 한 서버가 다시 켜질 때, 다른 서버에서 정상으로 돌고 있는 긴 적재까지 실패로 덮을 수 있었습니다.

06요청 제한 · 서버 두 대, DB 하나

서버가 두 대여도 요청 제한이 느슨해지지 않게 했습니다

요청 횟수를 서버 메모리에서 세면, 서버 수만큼 한도가 늘어납니다. 그래서 공유 테이블 한 줄을 두 서버가 함께 세게 했습니다. 확인부터 하면 두 서버가 동시에 통과시킬 틈이 생기므로, 먼저 1을 더하고 더한 값으로 한도를 봅니다.

서버마다 따로 세면

10회

로그인 한도가 10분에 5회여도, 서버 두 대가 따로 세면 10회까지 통과합니다.

DB에서 함께 세면

5회

어느 서버로 들어와도 같은 줄을 세서, 한도가 그대로 지켜집니다.

  1. 처음 들어온 키가 부딪힐 때같은 키가 동시에 처음 들어와 기본 키가 부딪히면 UPDATE로 한 번 더 시도해, 세는 데서 빠지는 요청이 없게 했습니다.
  2. 같은 방식을 다른 한도에도관리자 로그인과 아이디 중복 확인에도 같은 카운터를 씁니다. 한도는 각각 30분에 10회, 1분에 30회입니다.

MERGE 한 문장으로 증가와 윈도 초기화를 함께

MERGE INTO RATE_LIMIT_BUCKET b
USING (SELECT ? RATE_KEY, ? NOW_AT, ? CUTOFF_AT FROM dual) s
   ON (b.RATE_KEY = s.RATE_KEY)
 WHEN MATCHED THEN UPDATE SET
      b.HIT_COUNT = CASE WHEN b.WINDOW_STARTED_AT < s.CUTOFF_AT
                         THEN 1 ELSE b.HIT_COUNT + 1 END, ...
 WHEN NOT MATCHED THEN INSERT ... HIT_COUNT = 1
더한 뒤의 값으로 한도를 확인합니다

윈도가 지났으면 1부터 다시 세고, 아니면 1을 더합니다. 처음 보는 키는 1로 들어갑니다.

07지도 · 상권 요약 조회 API

상권 경계와 지표 조회 API 분리

지도에는 상권 경계(GeoJSON)가 그려지고, 그 위에 매출과 유동인구 같은 숫자가 얹힙니다. 경계는 무겁고 거의 바뀌지 않지만, 숫자는 필터를 바꿀 때마다 새로 필요합니다. 그래서 두 가지를 다른 API로 나눴습니다.

  1. 경계는 /geo, 숫자는 /summary필터를 바꾸면 /summary만 다시 부르고, 경계는 처음 받은 것을 그대로 씁니다.
  2. 적재 시점이 달라도 빈 값이 나오지 않게네 데이터를 쿼리 하나로 모으는데, 데이터마다 적재된 분기가 달라 한 분기로 맞추면 빈 칸이 생길 수 있었습니다. 그래서 매출의 최신 분기를 기준으로 삼았습니다.
  3. 결과에 상한을 두었습니다요약은 2만 행까지, 매출 목록은 필터를 꼭 받고 5,000행까지만 돌려주며, 잘렸는지를 응답에 표시합니다.
  4. 응답과 예외는 한 가지 모양으로모든 API가 같은 응답 형식을 쓰고, 제약 위반과 낙관적 락 충돌은 409, 처리하지 못한 예외는 내부 메시지를 숨긴 500으로 돌려줍니다.
