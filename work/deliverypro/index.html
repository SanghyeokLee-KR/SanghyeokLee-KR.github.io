01개요

주문부터 묶음배달까지, 네 가지 역할을 한 흐름으로 이었습니다

사용자는 가게를 고르고 주문하고, 사장님은 주문을 받고 메뉴를 관리하고, 라이더는 배달을 맡고, 관리자는 회원과 가게와 라이더를 운영합니다. 이 네 역할을 한 서비스 안에서 잇는 배달 플랫폼을 다섯 명이 함께 만들었습니다.

조장으로서 저는 라이더 한 명이 여러 집을 어떤 순서로 돌지를 서버가 계산하게 했고, 다섯 명이 만든 API가 같은 모양으로 응답하도록 서버 공통 규약을 맞췄습니다. 네이버 · 구글 · 카카오 소셜 로그인과 화면도 맡았습니다.

14.58km

배달지 5곳을 도는 경로

약 38분, 방문 순서는 정확한 답. 데모 데이터 기준.

12곳

정확한 답을 구하는 정차지 수

그보다 많으면 근사로 내려가고 그 사실을 표시합니다.

1,876m

직선 208m인 두 집의 도로 거리

건널 수 없는 길을 돌아가야 해서 생긴 차이.

247.7초

같은 두 집, 갈 때 걸리는 시간

올 때는 97.6초. 일방통행이 반영된 결과.

02묶음배달 경로 계산

직선거리 대신, 도로망 위에서 방문 순서를 정했습니다

직선거리로 순서를 정하면 일방통행도, 건널 수 없는 길도 반영되지 않습니다. 그래서 도로망을 방향이 있는 그래프로 만들고, 그 위에서 정차지끼리 걸리는 시간을 구한 다음 순서를 정했습니다. 도로망은 실제 지도 데이터가 아니라, 일방통행과 건널 수 없는 길을 담아 만든 데모용 격자(25×21)입니다. 장면을 골라 계산이 지나가는 길을 따라가 보세요.

  1. CSR graph

    방향이 있는 도로망

    교차로를 점, 도로 구간을 선으로 둔 방향 그래프입니다. 선의 값은 거리가 아니라 도로 종류별 속도로 구한 소요 시간입니다.

  2. snap · 400m

    가까운 교차로에 붙이기

    배달지를 400m 격자 색인으로 가장 가까운 교차로에 붙이고, 1,500m 넘게 떨어지면 구역 밖으로 봅니다.

  3. Dijkstra

    정차지마다 한 번

    정차지마다 다익스트라를 한 번 돌려 정차지끼리의 소요 시간표를 만듭니다. 목적지를 다 찾으면 바로 멈춥니다.

  4. Held-Karp

    방문 순서

    12곳까지는 정확한 답을 구하고, 그보다 많으면 최근접 이웃과 2-opt 근사로 내려가며 정확한 답인지 함께 표시합니다.

  1. 순서와 경로를 한 번에계산한 순서는 DB에 저장하고 구간 좌표와 함께 돌려줘, 화면의 경로와 저장된 순서가 어긋나지 않게 했습니다.
  2. 같은 교차로에 붙은 두 집교차로까지 걸어가는 거리를 도보 속도로 바꿔 구간 양 끝에 더합니다. 같은 교차로에 붙은 두 집 사이가 0초로 나오지 않게 하려는 것입니다.

03그래프가 제대로 도는지

일방통행이 정말 반영되는지, 숫자로 테스트에 고정했습니다

그래프가 실제로 작동하는지는 돌아가야 하는 사례로 확인했습니다. 건널 수 없는 길 반대편에 있는 두 집은 직선으로는 가깝지만, 도로로는 한참 돌아가야 합니다. 같은 두 집이라도 가는 방향에 따라 걸리는 시간이 달라야 일방통행이 비용에 들어간 것입니다.

직선으로 재면

208m

지도 위에서 두 집 사이를 곧게 이은 거리입니다.

도로를 따라가면

1,876m

건널 수 없는 길을 피해 돌아가는, 하나뿐인 우회로입니다.

갈 때

247.7초

같은 두 집을 한쪽 방향으로 갈 때 걸리는 시간입니다.

올 때

97.6초

반대 방향은 두 배 넘게 빠릅니다. 일방통행이 비용에 들어갔다는 뜻입니다.

직선으로 208m인 두 집이 도로로는 1,876m였고, 갈 때 247.7초, 올 때 97.6초가 걸렸습니다.

일방통행이 그대로 반영된다는 걸 이 값으로 테스트에 고정해 두었습니다. 도로망을 손대면 문서가 아니라 테스트가 먼저 깨집니다. 방문 순서도 모든 순서를 다 따져 본 답과 같은지 테스트로 확인합니다.

04조장으로 맡은 서버 공통 부분

다섯 명이 만든 API가 같은 모양으로 응답하게 맞췄습니다

처음에는 API마다 응답 모양이 달랐고, 실패를 null이나 true/false로 알리는 곳도 있었습니다. 그래서 응답 봉투 하나와 오류 코드 여덟 가지, 업무 예외 하나로 통일했습니다.

상태오류 코드
400BAD_REQUEST
400VALIDATION_ERROR
401UNAUTHORIZED
403FORBIDDEN
404NOT_FOUND
405METHOD_NOT_ALLOWED
409CONFLICT
500INTERNAL_SERVER_ERROR
  1. 예전 핸들러와 부딪히지 않게이름이 같은 예전 핸들러가 남아 있어서, 새 핸들러는 이름을 따로 주고 @RestController에만 걸리도록 범위를 좁혔습니다.
  2. 트랜잭션은 서비스에서트랜잭션 경계를 서비스 계층으로 옮기고 조회에는 readOnly를 붙였습니다. open-in-view를 꺼서 지연 로딩이 화면까지 새어 나가지 않게 했습니다.
@RestControllerAdvice(name = "restGlobalExceptionHandler",
                      annotations = RestController.class)
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    ... ApiResponse.fail(errorCode, ex.getMessage())
}

05소셜 로그인과 바로 실행되는 구성

로그인은 세 곳과 직접 주고받고, 누구나 받아서 바로 돌려 볼 수 있게 했습니다

소셜 로그인 3사Apache HttpClient

네이버 · 구글 · 카카오의 인가 코드 교환과 프로필 조회를 Apache HttpClient로 직접 호출했습니다. 카카오는 응답 구조가 달라 따로 읽었고, 비밀번호는 BCrypt로 저장합니다.

Oracle 없이도 실행h2 프로파일

h2 프로파일에서는 Oracle 호환 모드로 띄우고 데모 데이터를 넣습니다. 데모 데이터는 이 프로파일에서만 들어가 운영 설정에는 영향이 없습니다.

지도 키가 없어도SVG

지도 키가 없으면 서버가 계산한 경로를 SVG로 그립니다. 덕분에 저장소를 받은 사람 누구나 경로 계산까지 바로 돌려 볼 수 있습니다.

./gradlew bootRun --args='--spring.profiles.active=h2'
Oracle과 외부 API 키 없이, H2 메모리 DB와 데모 데이터로 뜹니다
