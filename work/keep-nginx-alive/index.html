01개요

root 권한을 가진 공격자가 들어와도, 채점 페이지는 늘 살아 있어야 했습니다

교수님이 root 권한으로 서버에 들어와 nginx를 끄고 포트를 빼앗는 공격/방어 CTF였습니다. 규칙상 공격자를 차단할 수 없어서, 막는 대신 쓰러져도 바로 일어나고, 그래도 안 되면 다른 서버로 비켜서는 구조를 만들었습니다.

서버 안에서는 서로 다른 복구 장치 다섯 가지가 nginx를 되살립니다. 그래도 페이지가 오염되면 그 서버는 스스로 로드밸런서에서 빠지고, 같은 구성의 다른 서버가 채점을 받습니다. 공격자의 명령과 서버 상태는 Teams와 직접 만든 관제 화면으로 실시간으로 지켜봤습니다.

02경기 규칙

막을 수 없다면, 쓰러져도 바로 일어나게 만들기로 했습니다

공격자는 서버에 root로 들어옵니다. 프로세스를 강제로 끄고, 서비스를 멈추거나 막고, 예약 작업을 지우고, 파일을 바꾸고, 포트를 먼저 차지할 수 있습니다. 그래서 서버 안의 어떤 방어도 마지막 방어선이 될 수 없다고 보고 출발했습니다.

  1. 공격자가 할 수 있는 일프로세스를 죽이거나 조작하고, 특정 포트를 먼저 차지해 웹 서비스를 막을 수 있습니다. 단, DDoS 같은 가용성 공격과 OS를 망가뜨리는 공격은 하지 않습니다.
  2. 방어 측이 못 하는 일공격자의 권한·접속·명령을 제한할 수 없습니다. 제한하면 규칙 위반입니다.
  3. 채점 방식제출한 주소를 5분 간격으로 헬스체크합니다. 연속 2회 오류까지는 감점이 없고, 3회째부터 감점됩니다.
  4. 그래서 세운 목표자동 복구로 다운 시간을 채점 기준 아래로 줄이고, 끝내 오염되면 그 서버가 스스로 채점에서 빠지게 하는 것입니다.

03방어 구조 · AWS 위의 서버 세 대

공격이 들어오면, 서버 안에서 일으키고 밖에서 비켜섭니다

채점 봇이 보는 주소는 로드밸런서(NLB) 하나입니다. 그 뒤에 서버 세 대를 두고, 공격자가 들어올 수 있는 SSH는 #1 하나에만 열었습니다. 아래에서 장면을 고르면 평소의 채점과 실제로 받은 세 번의 공격이 어떤 길을 지나는지 순서대로 볼 수 있습니다.

저장소의 구성도와 공격 기록을 옮겨 그렸습니다. 원본 구성도 보기

  1. 공격 표면은 #1 하나로#2와 #3은 #1을 AMI로 복제한 같은 구성의 서버입니다. 보안 그룹에서 22번을 막아, 공격자가 들어올 수 있는 서버를 #1 하나로 좁혔습니다.
  2. 정상의 기준은 하나로감시 스크립트, cron, 헬스체크가 모두 같은 기준으로 정상을 판단합니다. 응답 본문에 채점 페이지의 제목인 ‘NginX를 살려라’가 h1으로 들어 있어야 정상입니다.
  3. 가용성의 본체는 구조입니다#1이 통째로 무너져도 #2와 #3이 채점 트래픽을 받습니다. 서버 한 대의 복구력보다 로드밸런서 헬스체크와 복제 서버가 더 큰 몫을 합니다.
  4. 설치는 Ansible로 다시 할 수 있게스크립트와 systemd 서비스, cron, auditd 규칙을 같은 결과로 다시 배포할 수 있도록 Ansible playbook으로 정리했습니다.

04다섯 겹의 복구 · #1 서버 안

한 줄을 끊어도 다른 줄이 살리도록, 복구 장치를 다섯 겹으로 겹쳤습니다

서로 다른 방식의 장치 다섯 가지가 nginx를 지켜봅니다. 공격자가 하나를 끊어도 남은 장치가 nginx와 끊긴 장치를 함께 되살립니다. 여럿이 한꺼번에 고치려다 부딪히지 않도록, 다시 띄우는 일은 flock으로 한 번에 하나씩만 하게 했습니다.

무엇이얼마마다
1systemd 재시작
강제로 꺼지면 바로 다시 띄웁니다		2초
2감시 스크립트 A·B
응답 본문을 검사하고, 80번을 차지한 프로세스를 치우고, 서로를 살립니다		5초
3cron
index.html을 되돌리고 nginx를 다시 띄우며, 감시 스크립트와 자기 자신도 되살립니다		1분
4무결성 감시
감시 스크립트가 켜져 있고 부팅 때 켜지게 되어 있는지 지킵니다		10초
5systemd 밖의 독립 감시
systemctl에 기대지 않는 다른 복구 경로입니다		3초
  1. 중요한 파일은 잠가 두었습니다chattr +i로 index.html, nginx.conf, nginx 실행 파일을 바꿀 수 없게 했습니다. root는 한 줄로 풀 수 있지만, 바꾸려면 한 단계를 더 거쳐야 하고 그 흔적이 감사 로그에 남습니다.
  2. 서버 안의 방어는 시간을 버는 일입니다로컬 장치의 역할은 다운 시간을 채점 기준 아래로 줄이고, 끝내 오염되면 서버를 빼는 신호를 주는 데까지로 정했습니다.

05스스로 빠지기 · 헬스체크와 로드밸런서

오염된 페이지를 내보내느니, 차라리 채점에서 빠지게 했습니다

#1의 헬스체크 스크립트는 2초마다 자기 페이지를 직접 요청해 본문을 검사합니다. 정상이면 ok 파일을 두어 /healthz가 200을 내고, 오염되면 그 파일을 지워 503을 냅니다. 로드밸런서는 503을 낸 #1을 대상 그룹에서 빼고, 채점 요청을 #2와 #3으로 보냅니다. 페이지가 돌아오면 #1은 다시 대상에 들어갑니다.

# healthz-checker.sh (줄여서 옮김) · 2초마다
if curl -s -m 3 http://127.0.0.1:80/ | grep -qF "$NEEDLE"; then
  echo "healthy" > /var/www/health/ok   # 정상 → 200
else
  rm -f /var/www/health/ok                # 오염 → 503
fi

ok 파일은 일부러 잠그지 않았습니다. 잠가 두면 페이지가 오염돼도 계속 200이 나가, 오염된 페이지가 그대로 채점됩니다.

05-2이웃이 감시하기

#1이 스스로 판단하지 못할 때를 대비해, #2가 밖에서 한 번 더 봤습니다

로드밸런서의 헬스체크는 #1이 스스로 내는 /healthz를 믿습니다. 공격자가 #1 안에서 헬스체크를 조작해 거짓 200을 내면 놓칠 수 있습니다. 그래서 깨끗한 복제 서버인 #2에서 tg-guardian이 #1과 #3의 실제 응답을 3초마다 검증하게 했습니다. 변조나 다운을 알아채면 AWS CLI로 그 서버를 대상 그룹에서 빼고, 정상으로 돌아오면 다시 등록합니다. #2에는 대상 등록·해제와 상태 조회만 할 수 있는 IAM 권한만 주었습니다.

06세 번의 공격 · 실제 경기 기록

세 번의 공격을 받았고, 세 번 모두 서비스는 살아 있었습니다

공격자가 친 명령은 auditd로 모두 모아 관제 화면에 바로 올렸습니다. 아래 시각과 명령은 그 화면에 남은 기록입니다.

  1. 1차

    감시 스크립트를 무력화하고 정찰했습니다

    감시 스크립트와 nginx를 한꺼번에 껐지만, 남아 있던 다른 복구 장치가 1분 안에 되살렸습니다.

  2. 2차

    apache2를 설치해 80번 포트를 빼앗았습니다

    팀원이 직접 정리하는 동안, 그 서버는 스스로 빠지고 로드밸런서가 다른 서버로 우회해 끊김이 없었습니다.

  3. 3차

    nginx가 다시 켜지지 못하게 막았습니다

    systemctl mask로 막힌 것을 감시 스크립트가 풀고 다시 띄웠습니다.

1차 · 관제 화면의 명령 기록

  1. 00:03:44감시 스크립트와 nginx를 한꺼번에 강제로 끕니다.pkill -9 -f "nginx_.*_watch.sh"; systemctl stop nginx; pkill -9 -x nginx
  2. 00:04:59docker가 돌고 있는지 살펴봅니다.ps -ef | grep docker
  3. 00:05:18.ssh 폴더를 열어 봅니다.cd .ssh/
  4. 00:05:49예약 작업을 확인합니다.crontab -l

2차 · 관제 화면의 명령 기록

  1. 07:50:42apache2를 설치합니다.apt-get install apache2
  2. 07:50:47nginx를 멈추고 끈 뒤, 80번 포트를 비우고 apache2를 띄웁니다.systemctl stop nginx; systemctl disable nginx; fuser -k 80/tcp; systemctl start apache2
  3. 07:57:34한 번 더 80번을 비우고 apache2를 띄운 뒤, 포트를 누가 쥐고 있는지 확인합니다.fuser -k -9 80/tcp; pkill -9 -f nginx; systemctl start apache2

07관제와 알림 · 직접 만든 화면과 Teams

공격자가 무엇을 치는지, 서버가 어떤 상태인지 바로 보이게 했습니다

auditd로 실행된 명령을 모으고, 감사 로그를 따라 읽으며 사건 번호로 짝을 맞춰 명령 기록을 만들었습니다. 이 기록과 서버 상태를 경기 중에 직접 만든 관제 화면에 올렸고, 로그인·명령·다운과 복구는 Power Automate를 거쳐 Teams 세 채널로 바로 알렸습니다.

  1. 사람의 눈도 겹쳤습니다채점은 24시간 돌아갑니다. 자동 복구가 대부분을 처리했지만, 세 명이 Discord로 교대표를 짜 새벽 불침번을 섰습니다.
  2. 다른 팀과도 서로 지켜봤습니다규칙상 의무는 없었지만 3·5·6조가 서로의 채점 기록을 10초마다 모아 보고, 어느 팀이든 오류가 나면 알려 주기로 했습니다.

08결과와 배운 점

망가진 서버를 끝까지 붙잡기보다, 빼고 바꾸는 쪽이 실무에 가까웠습니다

서버 안에서 끝까지 버티기보다, 망가진 서버를 빼고 새것으로 바꾸는 쪽이 실무에 가깝다는 것을 배웠습니다. 이 생각이 failstop의 증설과 교체 구조로 이어졌습니다.

  1. 가용성은 서버 한 대가 아니라 구조에서 나옵니다경기 내내 서비스가 살아 있었던 가장 큰 이유는 #1의 복구력보다 로드밸런서와 복제 서버였습니다.
  2. 잠그는 것이 늘 안전하지는 않습니다헬스체크 파일을 잠그지 않은 덕분에, 오염된 서버는 버티지 않고 빠졌습니다. 무엇을 지키는지부터 정해야 무엇을 잠글지도 정해집니다.
  3. 자동화 위에 사람의 눈을 겹쳤습니다2차 공격처럼 사람이 직접 정리해야 하는 순간이 있었습니다. 그래서 자동 복구 위에 관제 화면과 알림, 새벽 불침번을 겹쳤습니다.
