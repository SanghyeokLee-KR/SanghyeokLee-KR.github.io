01개요

같은 시간에 모이지 않아도, 악기가 없어도 합주가 되게 하고 싶었습니다

밴드 합주에는 같은 시간과 같은 장소, 그리고 악기를 다룰 줄 아는 사람이 필요합니다. 하모니는 이 세 가지를 없애는 데서 출발했습니다. 코드 패드를 누르면 소리가 나고, 친구가 올린 트랙 위에 내 연주를 얹으면 합주가 됩니다. 회원가입 없이 닉네임만 넣으면 바로 시작합니다.

저는 4인 팀의 팀장으로 제품과 정책을 정했고, 출시 직전 독립 검토에서 막힌 보안 문제를 해결하고 최종 승인을 맡았습니다. 서버 구현은 백엔드 담당 팀원이 이끌었습니다. 7일 안에 실제로 배포해 쓸 수 있는 상태까지 만드는 것이 목표였고, 6월 26일 토스 앱에 전체 공개로 출시했습니다.

02합주 방식

실시간으로 맞추지 않고, 트랙을 한 겹씩 얹는 방식을 택했습니다

실시간으로 소리를 주고받으며 합주하면 네트워크 왕복 시간 때문에 박자가 어긋납니다. 그래서 각자 메트로놈에 맞춰 자기 트랙을 녹음하고, 같은 공유 코드의 곡에 얹는 방식으로 정했습니다. 화면은 1.5초마다 서버에서 곡을 다시 받아 와 새 트랙을 합칩니다.

  1. 혼자 하는 연주는 서버에 가지 않습니다녹음과 편집은 기기 안에서 끝납니다. 공유를 누를 때만 곡이 서버로 갑니다.
  2. 6자리 공유 코드곡을 올리면 서버가 코드를 만들어 돌려줍니다. 친구는 그 코드로 곡을 열고 트랙을 얹습니다.
  3. 1.5초마다 다시 받아 옵니다다른 사람이 트랙을 추가하자 1.8초 안에 트랙 수가 1에서 2로 바뀌었습니다(통합 시험 IT-CL-06).
  4. 가입 없이 익명 키로토스가 주는 익명 키로 사용자를 구분합니다. 로그인과 회원가입은 이번 범위에서 뺐습니다.

03출시 전 보안 검토

공개된 코드 하나로 남의 곡을 바꿀 수 있다는 걸, 출시 직전에 알았습니다

계정 없이 코드만으로 들어오는 구조라, 커뮤니티에 곡을 공개하는 기능을 붙이기 전에 독립 검토를 받았습니다. 결함은 Codex 독립 검토가 처음 찾았고, 판정은 출시 불가였습니다. 저는 검토에서 나온 문제를 하나씩 해결하고 다시 검토를 받는 일을 맡았습니다. 아래 그림에서 장면을 고르면, 고친 뒤의 서버가 각 요청을 어떻게 처리하는지 볼 수 있습니다.

실제 배포 구성을 옮겨 그렸습니다. 결과 숫자는 통합 시험 결과서의 기록입니다.

검토가 찾은 문제와 고친 방법

  1. 권한

    공개된 곡 코드만 알면 남의 곡에 트랙을 붙일 수 있었습니다

    공개된 곡은 작성자 키가 같을 때만 붙일 수 있게 하고, 다르면 403을 돌려줍니다. 남의 곡을 쓰려면 원본을 표시한 새 곡(origin_code)을 만들게 했습니다. 비공개 곡은 코드가 곧 열쇠라, crypto.randomInt로 만들어 추측하기 어렵게 했습니다.

  2. 신고

    키만 바꿔 신고하면 남의 댓글을 숨길 수 있었습니다

    신고자와 요청 제한의 기준을 서버가 확인한 IP로 바꿨습니다. nginx가 클라이언트가 보낸 X-Forwarded-For를 실제 접속 주소로 덮어쓰고, 앱은 127.0.0.1에만 열어 두었습니다.

  3. 재시도

    다시 보내면 같은 곡이 여러 번 올라갔습니다

    멱등 토큰을 '요청한 사람의 키 + 토큰'으로 묶고, 첫 트랙 내용의 해시로 같은 곡을 알아봐 이미 있는 코드를 돌려줍니다. 다른 작성자가 같은 토큰을 보내도 원래 작성자의 코드를 받아 가지 못했습니다.

검토를 다시 받기까지

  1. 06-23첫 검토에서 출시 불가 판정. 공개 곡 오염, 신고 우회, 요청 제한 우회가 막아야 할 문제로 나왔습니다.
  2. 06-23고친 뒤 두 번째 검토는 조건부 통과. 앱이 8080 포트로 바로 열리지 않는지 확인하라는 조건이 붙었습니다.
  3. 06-24앱을 127.0.0.1에만 열어 둔 것을 확인받고 세 번째 검토에서 통과했습니다.
  4. 06-26토스 앱에 전체 공개로 출시했습니다.

출시 불가 판정을 받은 항목을 모두 고친 뒤 다시 검토를 받아 통과했고, 그다음에 출시를 승인했습니다.

04서버 구조 · AWS EC2 한 대

밖에서는 nginx만 보이고, 앱과 DB는 서버 안쪽에만 두었습니다

서울 리전의 EC2 한 대에서 nginx가 TLS를 처리하고, 요청을 127.0.0.1:8080의 Node 앱으로 넘깁니다. 데이터는 SQLite 파일 하나에 저장합니다. 서버는 Node 내장 모듈만 써서 바깥 패키지에 기대지 않습니다. 배포는 제 승인 아래 진행했습니다.

  1. 전용 계정과 좁은 쓰기 권한앱은 systemd에서 전용 계정 harmony로 돌고, 권한 상승을 막고 시스템 경로를 읽기 전용으로 둡니다. 쓸 수 있는 곳은 data 디렉터리 하나입니다.
  2. 헤더는 nginx가 다시 씁니다클라이언트가 보낸 X-Forwarded-For를 이어 붙이지 않고 실제 접속 주소로 덮어씁니다. 앱은 TRUST_PROXY=1일 때만 그 값을 믿습니다.
  3. 여러 번 돌려도 안전한 테이블 변경컬럼 추가는 try로 감싼 ALTER TABLE이라, 이미 있는 DB에 다시 실행해도 문제가 없습니다.
  4. 중복 게시는 한 번의 트랜잭션 안에서찾기부터 저장까지 사이에 await가 없고, node:sqlite의 동기 API에 BEGIN과 COMMIT을 써서 경쟁 상태를 막았습니다.

systemd 서비스 파일과 nginx 설정(줄여서 옮김)

# /etc/systemd/system/harmony-api.service
[Service]
Environment=PORT=8080
Environment=TRUST_PROXY=1
ExecStart=/usr/bin/node /opt/harmony-api/server.mjs
Restart=on-failure
User=harmony
NoNewPrivileges=true
ProtectSystem=full
ProtectHome=true
ReadWritePaths=/opt/harmony-api/data

# nginx · 클라이언트가 보낸 값을 실제 접속 주소로 덮어씁니다
location /sessions {
  proxy_pass http://127.0.0.1:8080;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $remote_addr;
}
