01개요

프로젝트 개요

직접 만든 모의 거래소를 운영하기 위한 인프라입니다. 제 PC의 Docker에서 장애 시험을 먼저 하고, 가상 머신으로 서버를 다시 구성한 다음 AWS로 옮겼습니다.

사용자와 봇이 같은 주문 API로 주문을 넣으면 Java 매칭 엔진이 체결하고, 결과는 PostgreSQL 원장에 남습니다. 서버가 죽거나 DB가 끊겨도 주문 기록과 잔고가 어긋나지 않게 하는 데 가장 공을 들였습니다.

08주문 처리 · 백엔드

주문 API의 멱등성 처리

응답을 받지 못한 사용자는 같은 주문을 다시 보냅니다. 그때마다 새 주문이 생기면 안 되고, 들어갔는지 모르는 상태로 남아서도 안 됩니다. 그래서 주문 처리 경로를 네 단계로 나눴습니다.

  1. POST /orders

    주문 API

    클라이언트가 만든 주문 키로 같은 주문을 알아보고, 내용이 다르면 거절합니다.

  2. command_journal

    명령 저널

    엔진보다 먼저 DB에 커밋합니다. 리더 권한이 확인돼야 한 줄이 들어갑니다.

  3. engine

    매칭 엔진

    Spring도 I/O도 시계도 쓰지 않는 순수 Java라, 같은 명령이면 늘 같은 체결이 나옵니다.

  4. ledger

    원장과 잔고

    금액은 BigDecimal과 NUMERIC(40,18)로만 다루고, 자산마다 원장 합계는 0이어야 합니다.

  1. 주문 키는 클라이언트가 만듭니다client_order_id가 없으면 받지 않습니다. 서버가 키를 대신 만들면, 응답을 못 받고 다시 보낼 때마다 새 주문이 생길 수 있기 때문입니다.
  2. 같은 키면 내용을 비교합니다요청 본문을 JCS(RFC 8785)로 정규화한 뒤 SHA-256 해시로 비교합니다. 필드 순서나 공백이 달라도 같은 주문이면 같은 값이 나옵니다.
  3. 엔진보다 저널에 먼저 기록합니다명령을 command_journal에 커밋한 다음에야 엔진에 넘깁니다. 그래서 엔진이 처리한 명령은 빠짐없이 DB에 남아 있습니다.
  4. 커밋됐는지 모를 때는 DB에 다시 묻습니다기록하는 순간 연결이 끊기면, DB 함수로 저널에 실제로 들어갔는지 확인합니다. 그래도 답을 못 받으면 503을 돌려주되 주문 키는 지우지 않습니다.

09리더와 원장 · 앱 서버 두 대 중 주문장 쓰기는 리더 한 대

리더 리스와 epoch로 옛 리더의 쓰기 차단

리더만 기한이 있는 리스를 갖고, 리더가 바뀔 때마다 epoch를 1씩 올립니다. 문제가 되는 건 잠깐 멈췄던 옛 리더가 자신이 아직 리더라고 보고 쓰기를 계속하는 경우입니다. 그래서 권한 확인과 쓰기를 SQL 한 문장 안에서 처리했습니다.

-- 저널에 쓰는 SQL, 일부만 옮김
INSERT INTO command_journal (...)
SELECT ...
  FROM leader_lease
 WHERE holder = :me
   AND epoch = :epoch
   AND lease_until > clock_timestamp()
   FOR KEY SHARE;

세 조건 중 하나라도 맞지 않으면 0행이 들어가고 옛 리더의 쓰기는 실패합니다. 확인과 기록이 한 문장 안에 있어서 그 사이에 리더가 바뀔 틈이 없습니다.

  1. epoch 7

    서버 A가 리더

    리스를 쥐고 주문을 저널에 씁니다.

  2. 리스 만료

    서버 A가 잠깐 멈춤

    리스를 갱신하지 못해 기한이 지납니다.

  3. epoch 8

    서버 B가 이어받음

    리스를 가져가며 epoch를 하나 올립니다.

  4. 0행

    돌아온 서버 A의 쓰기

    epoch 7로는 조건이 맞지 않아 한 줄도 들어가지 않습니다.

장애 시험 중 찾아서 고친 문제4건 펼쳐 보기
  1. DB 지연

    DB를 느리게만 했는데 리더가 바뀌었습니다

    정산 트랜잭션의 FOR SHARE가 리스 갱신을 막고 있었습니다. FOR KEY SHARE와 유일 인덱스로 바꾼 뒤, 같은 시험 세 번 모두 리더가 그대로였습니다.

  2. 연결 끊김

    연결이 끊기면 리더 없이 멈췄습니다

    트랜잭션을 연 채 멈춘 세션이 잠금을 쥐고 있었습니다. DB에 10초 제한과 keepalive를 걸자 13.9초 만에 이어받았습니다.

  3. 리더 교대

    새 리더가 이미 끝난 리스를 받았습니다

    만료 시각을 잠금을 기다리기 전부터 세고 있었습니다. 잠금을 얻은 뒤부터 세도록 고치자 이어받기가 10초 안팎으로 고르게 나왔습니다.

  4. 옛 리더

    물러난 리더가 500을 돌려줬습니다

    리더가 아닌 서버는 503을 돌려주게 바꿨습니다. 그 뒤로 다시 돌린 시험에서는 주문 500이 한 건도 나오지 않았습니다.

09-2원장 검증

장애 후 원장 정합성 SQL 검사

장애 시험 후 매번 확인하는 세 가지 · 한 행이라도 어긋나면 실패

  • 자산마다 원장 합계가 0인가
  • 잔고가 원장을 다시 계산한 값과 같은가

이 검사로 비동기 복제에서는 확인해 준 주문도 사라질 수 있다는 것을 확인했습니다. 그래서 Patroni 엄격 동기 복제로 바꾸고, 동기 예비 DB가 없으면 앱이 주문을 423으로 막게 했습니다.
