주 DB 전원을 바로 끊었을 때: 승격 23.0초, 유실 0건

개인 AWS 서울 리전의 Patroni 두 노드에서 주 DB 커널에 sysrq 전원 차단을 걸었습니다. 예비 DB가 23.0초 뒤 승격했고, 직전 60초 동안 커밋된 주문 196건과 체결 129건이 모두 새 주 DB에 있었습니다. 엄격 동기 복제라 옛 주 DB가 예비로 돌아온 뒤에야 주문이 다시 커밋됐고, 그 시각은 장애 후 70.1초였습니다.

환경
개인 AWS 서울 리전. PostgreSQL + Patroni db-1·db-2(엄격 동기), etcd 3표. 시각은 서버 시계(UTC)
주입
주 DB db-2에서 echo o > /proc/sysrq-trigger(종료 절차 없는 전원 차단)
결과
승격 +23.0초, 첫 주문 커밋 +70.1초, 주문 196/196·체결 129/129
관련 작업
failstop

시험을 다시 설계한 이유

이전에 적어 둔 승격·재개 시간은 원자료가 저장소에 남아 있지 않아서, 같은 날 두 회차를 다시 쟀습니다. 1회차는 주 DB db-1을 aws ec2 stop-instances --force로 껐습니다. 그런데 OS가 종료 절차를 밟으면서 02:03:17에 PostgreSQL과 Patroni를 먼저 내렸고, Patroni가 리더 키를 놓자 db-2가 1.07초 만에 승격했습니다. 정상 종료로 내려간 주 DB를 잰 셈이라, 갑작스러운 서버 장애를 보려면 다른 방법이 필요했습니다.

2회차는 주 DB(db-2)에서 커널에 전원 차단을 직접 걸었습니다. 주입 시각을 디스크에 먼저 적고 sync한 뒤 끊습니다. 명령은 SSM으로 보냈습니다.

# db_failover_test2.sh가 db-2에 보내는 명령
date +%s.%N > /var/tmp/failstop-t0 && sync && echo o > /proc/sysrq-trigger

이 서버의 kernel.sysrq는 16이지만, 이 값은 키보드 입력에만 적용되고 root가 /proc/sysrq-trigger에 쓰는 동작은 막지 않습니다. OS 종료 절차가 돌지 않으므로 Patroni는 리더 키를 놓지 못하고, 예비 DB는 키가 만료될 때까지 기다려야 합니다.

유실을 센 방법

주입 직전에 주 DB에서 최근 60초 동안 커밋이 보인 주문(command_journal의 NEW)과 체결(trades) 번호를 적어 두고, 장애 뒤 새 주 DB에 그 번호가 모두 있는지 셌습니다. 엄격 동기에서는 다른 세션에 보인 커밋이면 동기 예비가 이미 WAL을 받은 것입니다. DB 조회는 DB 서버에서 postgres 계정 peer 인증으로 했습니다.

SELECT json_build_object('t', extract(epoch FROM clock_timestamp()),
  'orders', (SELECT coalesce(json_agg(seq), '[]') FROM (SELECT seq FROM command_journal
             WHERE command_type = 'NEW' AND created_at > now() - interval '60 seconds' …) o),
  'trades', (SELECT coalesce(json_agg(id), '[]') FROM (SELECT id FROM trades
             WHERE created_at > now() - interval '60 seconds' …) t));

승격과 쓰기 보류

db-1의 Patroni 로그입니다. 02:17:50까지는 db-2를 리더로 따르다가, 02:18:02에 리더 키를 얻어 승격했습니다.

02:18:02,040 INFO: promoted self to leader by acquiring session lock
02:18:02.042 UTC [2071] LOG:  received promote request
02:18:03,231 WARNING: No standbys available!
02:18:03,232 INFO: Assigning synchronous standby status to ['*']
02:18:03,333 INFO: no action. I am (db-1), the leader with the lock

승격까지 23.0초는 Patroni 설정 ttl: 30, loop_wait: 10에서 옛 리더 키가 만료되는 시점과 맞습니다. 승격 직후 동기 예비가 없으니 Patroni가 synchronous_standby_names를 '*'로 걸었고, 커밋은 예비가 붙을 때까지 기다립니다. 앱의 공개 상태 API도 이유를 database_unavailable에서 replication_unavailable로 바꿔 '거래 일시 중단'을 유지했습니다.

재합류와 대조 결과

db-2가 stopped가 된 것을 확인한 뒤 다시 켰습니다. Patroni가 기동하고 db-1을 기준으로 pg_rewind를 돌려 동기 예비로 돌아왔고, 그 뒤에 쓰기가 재개됐습니다.

직전 60초 동안 커밋이 보인 주문 196건과 체결 129건이 모두 새 주 DB에 있었습니다. 1회차도 주문 211건과 체결 127건이 모두 있었습니다.

거래 재개 70.1초는 옛 주 DB를 승격 직후 다시 켰기 때문에 나온 값입니다. 엄격 동기에서는 동기 예비가 없으면 쓰기를 멈추므로, 옛 주 DB가 돌아오지 않으면 운영자가 새 예비를 붙이거나 엄격 모드를 풀 때까지 거래가 멈춥니다. 재개 시간은 옛 주 DB가 언제 돌아오는지에 달려 있습니다. 공개 상태 API의 ACTIVE(+65.6초)가 첫 주문 커밋보다 약 4.5초 앞서므로, 70.1초는 실제 커밋 시각을 기준으로 한 값입니다.

1회차 재개 시간은 쓰지 않았습니다

1회차는 시험 도구가 db-1이 아직 stopping일 때 start-instances를 보내 IncorrectInstanceState로 거절됐는데, 도구가 이 오류를 확인하지 않아 약 10분 뒤에야 다시 켰습니다. 그동안 거래가 일시 중단됐습니다(공개 상태 API 기준 11:03:17~11:14:20 KST). 2회차 도구는 stopped를 확인한 뒤 켜고, 성공 응답까지 확인하도록 고쳤습니다.

대조 대상은 주입 직전 60초 동안 커밋이 보인 주문과 체결입니다. 목록을 적은 뒤 주입까지 약 4초 사이의 커밋은 대조에 들어가지 않았고, 클라이언트가 응답을 받은 주문을 하나하나 대조한 것도 아닙니다(로컬 시험의 ACK 기록기와 k6 대조는 개인 AWS에서 돌리지 않았습니다). 회차별 한 번의 값이라 반복 측정 분포는 없습니다.
