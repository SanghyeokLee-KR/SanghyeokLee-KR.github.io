비동기 복제에서 확인받은 쓰기 122건 중 36건이 사라졌습니다

로컬 Docker에서 PostgreSQL 비동기 복제의 primary를 강제 종료하고, 클라이언트가 커밋 확인(ACK)을 받은 행이 승격한 standby에 남아 있는지 셌습니다. standby를 8초 멈춘 회차에서는 ACK 122건 중 36건이 없었습니다. 이 결과를 근거로 DB 복제를 Patroni 엄격 동기로 바꾸고, 앱에는 동기 standby가 없을 때 쓰기를 거절하는 게이트를 넣었습니다.

환경
로컬 Docker 한 호스트, postgres:17-alpine 2대(각 메모리 512MiB), 비동기 스트리밍 복제
증상
standby 8초 정지 뒤 primary 급사: ACK 122건 중 36건 유실(29.5%)
결과
Patroni 엄격 동기 2노드로 전환 결정(ADR 0036), 동기 standby가 없으면 쓰기를 423으로 거절
관련 작업
failstop

당시 DB 구성

그때 DB는 primary 한 대와 standby 한 대의 비동기 스트리밍 복제였습니다. synchronous_standby_names를 비워 두었기 때문에 primary는 자기 디스크에 WAL을 쓰면 바로 커밋을 확인합니다. primary가 죽으면 사람이 standby를 승격하고 앱의 DB 주소를 바꾸는 수동 절차였습니다.

비동기 복제에 유실 창이 있다는 건 알고 있었는데요. 이 구성에서 몇 건을 잃는지는 잰 적이 없었습니다. 그래서 primary가 급사했을 때의 유실량과 승격 명령 시간, 옛 primary 재편입을 한 번의 주행으로 묶어 쟀습니다.

시험 방법

스크립트는 harness/scale/failover_rpo_check.py이고 배선은 deploy/compose.node-data.yml 그대로입니다. 쓰기 스레드가 한 트랜잭션에 한 행씩 INSERT … RETURNING n을 보내고, 서버가 값을 돌려준 번호만 ACK로 기록합니다. 동시에 다른 스레드가 20만 행 INSERT를 반복해 WAL을 만듭니다. 프로브만 돌리면 WAL이 거의 생기지 않아 복제가 밀리지 않으니까요.

회차는 두 개입니다. natural은 다른 조작 없이 primary를 죽였고, lagged는 docker pause로 standby를 8초 얼린 뒤 죽였습니다.

실행작업 PC Dockerfailover_rpo_check.py가 실행
# 스크립트가 실행하는 장애 주입과 승격 순서
$ docker pause <standby>                 # lagged 회차만, 8초
$ docker update --restart=no <primary>   # 재시작 정책이 옛 primary를 되살리지 않게
$ docker kill -s KILL <primary>
$ docker unpause <standby>
$ docker exec -u postgres <standby> pg_ctl promote -D /var/lib/postgresql/data

유실은 "ACK 받은 번호 중 승격한 노드에 없는 것"으로 셌습니다. 최댓값까지의 구간으로 세면 중간에 실패한 요청까지 유실로 잡히므로, ACK 번호 목록 전체를 넘겨 대조했습니다.

실행승격한 standby유실 대조 SQL
SELECT count(*) FROM unnest(ARRAY[…ACK 받은 번호…]::bigint[]) g
 WHERE NOT EXISTS (SELECT 1 FROM rpo_probe p WHERE p.n = g);

처음에는 공식 이미지가 초기화 중 임시 서버를 한 번 내리는 사이에 테이블 생성 DDL이 조용히 실패해, 테이블이 없는 채로 유실 0이 나온 적이 있었습니다. 그 뒤로는 주행마다 프로브 테이블이 standby에 복제됐는지 먼저 확인하고, ACK가 0건이면 주행을 멈추게 했습니다.

lagged 회차의 ACK 속도는 약 4.4행/s였습니다. 8초면 약 35행인데요. 실제 유실은 36행이었습니다. standby가 멈춰 있던 동안 primary가 확인해 준 쓰기가 거의 그대로 사라졌습니다. 이 구성에서는 복제 지연이 곧 유실량이고, natural 회차의 0건도 이 호스트와 이 부하에서 지연이 작았을 뿐입니다.

승격 명령 시간은 docker kill부터 승격한 노드가 쓰기를 받을 때까지입니다. 사람이 장애를 알아차리고, 승격을 판단하고, 앱 DB_HOST를 바꾸는 시간은 들어 있지 않아서 RTO로 쓰지 않았습니다.

옛 primary 재편입은 pg_rewind가 실패했습니다

wal_log_hints는 on이었지만 되감기에 필요한 WAL이 이미 없었습니다.

로그옛 primarypg_rewind
pg_rewind: servers diverged at WAL location 0/2F1BFFF0 on timeline 1
pg_rewind: error: could not open file ".../pg_wal/000000010000000000000021": No such file or directory
pg_rewind: error: could not find previous WAL record at 0/21FFFFC0

pg_rewind는 마지막 공통 체크포인트부터 WAL을 읽는데, 이번에는 그 지점이 분기 지점보다 209.8 MiB 앞이었습니다. wal_keep_size가 기본값 0인 상태에서 28초 동안 991.7 MiB를 썼으니 그 사이 세그먼트는 이미 재활용됐습니다. 결국 전량 베이스백업(428.7 MiB)으로 다시 붙였고, 스트리밍 재개 확인까지 272.549초가 걸렸습니다. 그동안 새 primary는 복제 상대 없이 혼자 돌았습니다.

Patroni 엄격 동기 복제로 바꿨습니다

2026-09-24~25에 유실 0을 가용성보다 앞에 두기로 하고 ADR 0036으로 기록했습니다.

  • PostgreSQL 두 노드를 Patroni가 관리하고, 리더 선출은 etcd 세 멤버(db-1, db-2, bot-1)로 합니다.
  • synchronous_mode: true, synchronous_mode_strict: true, synchronous_node_count: 1. primary는 standby가 WAL을 디스크에 쓴 뒤에만 커밋을 확인합니다.
  • Patroni는 /sync에 적힌 동기 standby만 자동 승격하므로, 승격된 노드는 확인된 커밋을 모두 가집니다.
  • 동기 standby가 없으면 비동기로 내려가지 않고 쓰기를 멈춥니다. 엄격을 끄면 눈에 보이는 정지가 보이지 않는 유실 위험으로 바뀌어서 그 선택지는 기각했습니다.

대가는 쓰기 가용성입니다. DB 한 대를 잃으면 그 노드가 standby로 돌아올 때까지 거래가 멈춥니다. 재합류용 wal_keep_size는 처음 16MB로 두었는데, 2026-09-27 로컬 시연 스택에서 재합류가 약 10분 막힌 뒤 1GB로 올렸습니다.

앱은 커밋이 멈추면 쓰기를 423으로 거절합니다

앱은 노드마다 1초에 한 번 pg_logical_emit_message 탐지 커밋을 보냅니다. 이 커밋이 2초 안에 끝나지 않고 원인이 SyncRep 대기로 확인되거나, synchronous_standby_names가 '*'이면 쓰기 가능 상태를 SUSPENDED로 바꿉니다. WriteGateFilter는 이 상태를 보고 쓰기 요청을 DB에 닿기 전에 거절합니다.

필터가 수용 제한 필터와 인증 필터보다 앞에 있어서, 거절할 때 요청 바디나 수용 허가, 멱등 키, 잔고 예약을 건드리지 않습니다. 조회 메서드는 이 필터를 거치지 않습니다. 503 대신 423을 쓴 건 인그레스 때문입니다. 503이면 인그레스가 쓰기 업스트림에서 리더를 빼서 계좌와 주문 조회까지 502가 되는데, 423은 proxy_next_upstream 목록에 없어 재시도와 퇴출이 일어나지 않습니다. 423은 "이 시도는 쓰지 않았다"는 뜻이고, 클라이언트는 재개 뒤 같은 멱등 키로 다시 보냅니다.

로컬 Docker에서 다시 확인한 결과

Patroni 4.1.5, etcd v3.5.34, HAProxy 3.0.27로 만든 폐기용 스택에서 장애 시나리오를 돌렸습니다. 2026-09-25 회차에서 primary 강제 종료(E-P1), primary 호스트 격리와 비대칭 격리(E-P3a·b), 봇·k6 부하 중 강제 종료(E-P5 두 번) 등이 PASS했고 확인받은 쓰기의 유실은 0이었습니다. 승격은 22.75~27.68초였습니다. 2026-09-27 시연 스택에서 거래 중 주 DB를 강제 종료한 여섯 회차도 회차마다 1만~2만 4천 건의 확인받은 쓰기 중 유실이 0이었습니다.

모두 로컬 Docker 한 호스트의 결과입니다. primary와 standby가 같은 커널과 디스크를 써서 AZ 간 지연이 없고, 비동기 회차는 조건마다 한 번씩만 돌렸습니다. 비동기 시험의 프로브는 psql로 쓴 행이라, 이 유실량은 주문 경로를 거치지 않은 저장 계층의 값입니다. Docker Desktop에는 /dev/watchdog이 없어 Patroni 워치독은 쓰지 않았습니다. AWS에서 잰 결과는 주 DB 전원 차단 시험에 따로 적었습니다.
