/api 504 진단: 가상 스레드와 HikariCP 라이브락

학교 AWS의 첫 앱 서버(app-1)에서 정적 웹과 Grafana는 응답하는데 /api/*만 30초 뒤 504를 냈습니다. 서비스는 active (running)였고 메모리, 디스크, DB 연결에도 문제가 없었습니다. 스레드 덤프에서 HikariCP 관련 스레드 세 개가 Thread.yield() 루프에 갇힌 것을 찾았고, 가상 스레드를 끄고 재시작해 복구했습니다.

환경
학교 AWS, app-1(2 vCPU, 메모리 1,909MiB). Spring Boot 앱을 systemd 서비스 exchange-app으로 운영하고 앞에 nginx
증상
/api/v1/markets 등이 30초 뒤 504, 호스트 안에서 직접 호출해도 15초 동안 응답 없음
결과
SPRING_THREADS_VIRTUAL_ENABLED=false 적용 후 재시작, 공개 /api/v1/markets 200(33ms)
관련 작업
failstop

상황

2026-09-21 08:18 UTC(17:18 KST)에 확인했습니다. nginx의 proxy_connect_timeout은 3초, proxy_read_timeout은 30초입니다. 앱 프로세스가 죽었다면 연결 거부로 바로 502가 나야 하는데 30초를 채운 504가 났으니, 8080 연결은 맺어지고 응답만 오지 않는 상태로 봤습니다.

작업 PC의 공인 IP 하나(/32)만 22번 포트로 허용하는 임시 보안 그룹 규칙을 추가하고 SSH로 접속했습니다. 원인을 찾을 때까지는 재시작이나 설정 변경 없이 읽기 전용 명령만 실행했습니다.

원인

세 지점은 모두 HikariCP의 ConcurrentBag이 연결을 기다리는 스레드가 있을 때 인계 큐에 연결을 넘기려 하고, 실패하면 Thread.yield() 후 다시 시도하는 구간입니다. 진행 없이 CPU만 쓰는 라이브락으로 판단했습니다.

앱은 spring.threads.virtual.enabled: true로 돌고 있었습니다. 요청을 처리하며 연결을 기다리는 쪽은 가상 스레드이고, 연결을 넘기는 쪽(connection-adder, housekeeper, market-catalog-refresh)은 플랫폼 스레드입니다. 2 vCPU에서 플랫폼 스레드 세 개가 yield 루프로 코어를 채우면 가상 스레드를 실어 나를 캐리어 스레드가 돌 여유가 줄고, 인계를 받을 쪽이 늦어지니 인계가 다시 실패합니다. 덤프의 스레드 번호(#1450104, #1450149)로 보면 기동 후 스레드가 백만 개 넘게 만들어졌습니다.

이 판단은 실행 중 상태를 관측한 결과이고, 같은 조건을 재현해 확정하지는 않았습니다. connection-adder는 덤프 시점에 만들어진 지 1,714초였고 CPU 시간은 871초였지만, 최초 계기는 찾지 못했습니다. 서비스 로그에는 30분 주기 WebSocket 통계만 있고 오류가 없었습니다. 풀 상한(요청 16, append 14, 리스 2)이 원인이라는 근거도 찾지 못했습니다.

JAR과 코드는 바꾸지 않았고, 저장소의 application.yml에 있는 spring.threads.virtual.enabled: true도 그대로 두었습니다. 이 서버만 환경변수로 덮어쓴 상태입니다. 기동은 12.7초가 걸렸습니다. 엔진이 마켓별 스냅샷을 채택하고 83건을 재생한 뒤 리더 리스를 epoch=6으로 얻었고, readiness가 08:22:07에 200을 반환했습니다.

가상 스레드를 끈 것은 문제가 난 경로를 피한 조치이고, HikariCP의 인계 실패 자체를 고친 것은 아닙니다. 같은 조합을 다시 켜면 재발할 수 있습니다. 부하를 올린 장시간 운영에서 플랫폼 스레드 풀이 충분한지는 이 작업에서 확인하지 않았습니다.
